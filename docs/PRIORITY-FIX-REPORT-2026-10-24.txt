1. SAVED BINDERS COULD PASS ONE CHECK AND FAIL ANOTHER

Original problem:
The saving side and opening side were using different rulebooks. The server could
accept an overlong cover subtitle or an invalid page color/border setting, but the
browser would refuse that same binder later. This could make a malformed saved
binder impossible to open through the normal app. It was a confirmed weakness,
not proof that anyone's existing binder is damaged.

What I changed:
The new database migration checks optional subtitles and page appearance using the
same limits as the browser. Empty optional subtitles still work. Colors must be
six-digit hex colors, and border choices must be recognized. It checks both the
binder default and settings for an individual page.

It does not rewrite saved records or remove older connected merged pockets. I did
not apply the audit's suggestion to reject old L-shaped imports, because both
existing loading systems accept them and suddenly banning them could break an
older binder. Creating new L-shaped merges remains disallowed by the editor.

How I checked:
I applied all migration files to an isolated test database. Valid settings still
pass. Invalid subtitles, invalid page settings and invalid save requests are
rejected without changing the previously saved binder. Emoji length limits match
the browser too. Existing ownership, restore, account isolation and backup checks
also pass.

Remaining limit:
This is a prepared migration, not a live database change. It prevents new bad
writes once deployed; it does not claim to repair previously malformed records.
The live database has not been scanned for existing affected records in this task.

2. DELETING PICTURES COULD SUCCEED BUT RETURN A FAILURE

Original problem:
Imagine the app deletes 60 pictures, then throws away the receipt because the
receipt is too long. The files may already be gone, but cleanup/account deletion
could still show an error. The request gateway allowed only a 16 KiB response,
which was smaller than a normal-looking response describing all 60 files.

What I changed:
The deletion route now allows a bounded 64 KiB response. That gives the existing
60-file operation room to return its result. The request size, access checks,
rate limits and all other route limits remain in place. This does not turn off
response protection or add automatic destructive retries.

How I checked:
A simulated response with metadata for 60 files now arrives intact. I tested it
both with a stated response length and as a streamed response without that header.
Responses beyond the new cap are still rejected. The account-deletion safety,
partial-failure and account-switch fixtures still pass.

Remaining limit:
No real artwork was deleted. The original failure and the fix were verified using
controlled responses, not a destructive test against the live service. The
updated gateway is not deployed yet.

3. CUSTOMIZATION COULD BE CHANGED UNDERNEATH AN UNFINISHED EDIT

Original problem:
Undo and Redo were first disabled while a customization panel was open, then a
later screen refresh accidentally enabled them again. Clicking one could change
the binder while its customization draft still described the old state.

There was a second problem: clicking a page thumbnail changed the page without
updating every customization control. The panel could still describe the old
page, while Apply would act on the newly selected page.

What I changed:
Undo and Redo stay disabled during customization. Their click handlers also check
that customization is closed. Canceling or applying restores normal history use.

Page arrows and thumbnails now use the same page-change function. It clears the
old selection and refreshes the card scope, style choices and preview. Binder
page-appearance controls also follow the actual page.

How I checked:
In an isolated browser, I placed a card, undid it to create a pending Redo, opened
customization, and confirmed both history buttons were disabled. Cancel restored
Redo, which still worked. I also switched between a populated page and an empty
page while customizing. The page scope became unavailable on the empty page and
returned on the populated page. Binder appearance correctly said Page 2 only
when page 2 was selected.
The automated UI fixtures also check that history clicks cannot change the draft
and that a page change clears the old selection and refreshes the preview/scope.

4. CARDS WITHOUT PICTURES LOOKED BROKEN OR BLANK

Original problem:
Some card pickers created a picture element even when there was no picture URL.
Others had incomplete handling when an image failed to load. The user could get a
broken-picture symbol or blank card space instead of an explanation.

What I changed:
The editor drawer, expanded picker, placeholder picker, viewer inspection and
collection picture controls share a small image helper. Missing pictures
immediately show a clean
Image unavailable placeholder. A picture that fails to load switches to the same
placeholder. It does not repeatedly retry a broken URL.

Binder pockets and the previews/viewer that use the shared SVG drawing also show
an explicit placeholder when the card picture is missing. Card names and IDs stay
available, so a missing picture does not prevent selecting or placing the card.
Discover already had its own missing-picture handling, which is preserved.

This does not fetch, invent, import or replace Pokemon artwork. A placeholder
means the picture is unavailable; it is not a recovered card image.

How I checked:
I tested empty URLs and deliberately broken images, including the browser's real
image-error event. The expanded picker displayed the placeholder, and a card with
no image could still be placed. The standalone viewer also showed the missing
picture placeholder in its card details dialog. The normal sleeve/toploader sizing tests still
pass, including small and merged pockets. Collection/repository tests also pass.

5. CLEARING FILTERS AND SEARCHING COULD GIVE MISLEADING FEEDBACK

Original problem:
Searching inside a filter hid options that did not match. Clear removed selected
filters but did not necessarily remove that internal search or unhide the options.
It could look as if choices had disappeared.

The pocket target-card search also sent a request for every typed character and
briefly said No matching cards while it was still waiting for the answer.

What I changed:
A filter's Clear button now clears its internal search and restores its options.
Clear all does this for every picker as well as resetting the actual filters.
Pending Discover search timers are canceled when clearing everything.

Pocket search waits for a short 250 ms typing pause. While waiting, it says
Loading cards. If loading fails, it shows the error and a Retry search button.
No matching cards appears only after a successful empty answer. Old answers
cannot replace a newer search. Closing the dialog cancels searches that have
not started and ignores late answers from searches already in progress.

How I checked:
Automated fixtures cover all six pickers, quick typing, out-of-order answers,
errors, retry and closing the dialog. Browser checks confirmed that Clear restored
all six Set options and Clear all restored the full 55-card sample list. The
pocket search visibly showed Loading cards, then the deliberate error and Retry,
and recovered when a new successful search was entered.

APPENDIX: ALL 33 ORIGINAL AUDIT GROUPS

The following statements describe what was found BEFORE this fix pass. Each item
also says whether it was fixed here, left for later, or was an incorrect claim.
This appendix preserves the distinction between an actual current failure and a
possible future problem.

A1: Expanded card browser creates broken images for empty URLs
Original verdict: Confirmed
Status: Fixed here: shared picture fallbacks.
editor-card-browser.js:195-207 always appends an image with thumbnail(card) and has no unavailable/error fallback. thumbnail() returns an empty string for an empty image URL. The prepared snapshot still has 1,590 empty source image fields; downloaded investigation files have not changed them. Correction: the cited editor.js:613-622 drawer also lacks a fallback, so the attachment's claim that this drawer already handles it is incorrect. A blank image is invalid/broken; do not assume every browser fetches the document itself for an empty image URL.

A2: Undo/Redo are re-enabled while customization is open
Original verdict: Confirmed
Status: Fixed here: history guard.
renderCoverControls() disables them at editor.js:1354-1357, but render() overwrites those values at 2030-2034. Click handlers at 2180-2184 call the state history methods without a coverOpen guard. The customizer is an interactive side panel, not a native modal that automatically prevents rail clicks.

A3: Page thumbnails skip customizer synchronization
Original verdict: Confirmed
Status: Fixed here: shared page navigation.
Thumbnail clicks at editor.js:2117-2122 change page/selection and call only render(). Arrow navigation at 2507-2522 additionally synchronizes style scope/choices and calls previewCover(). studio.refresh() only updates selection actions; it does not synchronize these controls. The old .page-strip is made inert, but the page list has already been moved into the sidebar.

A4: Editor Set filter fails in local fallback
Original verdict: Incorrect as a current editor bug
Status: Not changed in this priority pass; see the verdict and explanation.
The name-versus-ID inconsistency exists in the generic search helper, but this caller does not take the alleged path. CardCatalogue.enabled returns remote (card-catalogue.js:278-279). The editor invokes its search only when enabled (editor.js:678-679); when disabled, it uses its own local filter comparing c.setName === set (693). The editor does not pass colorEnabled, which is the other route into the helper's local search.

A5: Placeholder search lacks debounce and shows an empty state while loading
Original verdict: Confirmed
Status: Fixed here: debounced search and loading/error/retry states.
The input handler calls renderPlaceholderChoices() directly (editor.js:1943). Changed queries clear matches, immediately render the empty result note, and issue a request (1834-1900). Stale-response protection exists, but it is not a debounce or a loading message. The attachment uses an outdated function name.

B1: Underscore set IDs cause catalogue startup fallback
Original verdict: Conditional defect; not present in the current snapshot
Status: Not changed in this priority pass; see the verdict and explanation.
A fixture with set_test is rejected by the startup regex at card-catalogue.js:131, leaving remote mode false. However, none of the current 201 populated snapshot set IDs contains _. The register regex cited by the attachment validates card IDs, not set IDs; its argument about uniform set-ID validation is imprecise. The current catch also does not emit the quoted Invalid set row message.

B2: Registering remote metadata wipes curated sample palettes
Original verdict: Conditional defect; current import avoids it
Status: Not changed in this priority pass; see the verdict and explanation.
Reproduced: registering an otherwise valid existing sample with palette: [] changes its shared palette from three colors to zero. The shallow sampleCards array shares those objects. However, catalogue-import.cjs:107 preserves legacy.palette, and the actual full snapshot loses none of the sample palettes. This is an adapter robustness gap, not proof that the current catalogue's color matching is broken.

B3: Alphanumeric collector numbers sort incorrectly locally
Original verdict: Confirmed helper defect
Status: Not changed in this priority pass; see the verdict and explanation.
Reproduced with a valid same-set input: GG10, GG2, GG01 remains in that order under ascending number sort. The comparator returns NaN at discover-core.js:71; descending uses a lexical provider-ID fallback, not natural collector-number ordering. This does not establish the same failure in remote SQL search, which uses a different comparator.

B4: wPromo support is inconsistent across layers

Status: Not changed in this priority pass; see the verdict and explanation.
Import/registration/collection state support the key, while the finish labels, binder validation and SQL finish allowlist omit it. A synthetic wPromo-only card has no Discover finish choices. Crucial correction: the actual 21,256-card snapshot contains zero cards with wPromo true, so the empty-select scenario is not a current-data failure.

B5: Clear does not reset picker text-search visibility
Original verdict: Confirmed
Status: Fixed here: individual and full picker resets.
The picker input hides rows (discover-filter-pickers.js:102-104), while Clear resets only the select and checkbox state. sync() does not unhide rows or clear its search/empty message. Clear all resets forms but does not recompute those row visibility flags. A previously searched option list can remain restricted after clearing.

B6: Collection bulk edit bypasses account guards and persists changes
Original verdict: Partly true; consequence overstated
Status: Not changed in this priority pass; see the verdict and explanation.
The bulk-submit handler lacks the guards used by run() and open dialogs are not closed on account change. However, it does not call persist(); saving is explicit. Account change clears selected, so the handler's !selected.size guard prevents the claimed bulk edit in that scenario. Ordinary form apply/applyMany also check blocked and repository.check(). Closing stale dialogs and adding consistent guards are valid improvements; an actual cross-account write was not demonstrated.

B7: Missing Optional status; batch spread order; picker IDs

C1: Viewer omits metadata loading and shows Missing card

C2: Fullscreen failure permanently exposes viewer announcements

C3: Landing entrances, side-slide clicks and scene switchers
Original verdict: Mostly confirmed, with qualifications
Status: Not changed in this priority pass; see the verdict and explanation.
Customize entrances use raw node.animate() and are absent from DemoMotion's protected entrance set, so stopAnimations() can cancel them; the attachment's proposed DemoMotion.trackEntrance API does not currently exist. Cancellation can cause an abrupt appearance, not necessarily permanently invisible content because the pending class is already removed. Hero slide pointer clicks are deliberately excluded by event.detail === 0, while drag/wheel/dots work. Arrange/Discover scene buttons explicitly call playback.resume(), contrary to the general stop-after-interaction rule outside documented exceptions. These are interaction/consistency issues with different severities.

D1: SQL document validation omits subtitle/style/rectangle/unknown-key rules
Original verdict: Serious core finding confirmed; grouped explanation partly wrong
Status: Fixed here for subtitles and page styles. Legacy merges and ignored keys intentionally remain compatible.
With every migration applied to an isolated embedded PostgreSQL instance, a 61-character subtitle, invalid cover pageStyle and invalid individual pageStyle all return SQL-valid but fail browser BinderStore.validate(). Thus malformed data admitted through an API can become unreadable to normal clients/recovery. Unknown keys are accepted by both paths and normalized away by the client; that alone does not cause the claimed read failure. Connected L-shaped imports are also accepted by both validators, although the editor prevents creating new L-shaped merges. Tightening rectangle rules without checking legacy data could introduce a compatibility problem.

D2: 16 KiB gateway output cap can break artwork deletion
Original verdict: Limit and failure reproduced; live frequency unverified
Status: Fixed here: larger finite deletion-response cap; tested with controlled responses.
The DELETE route has a 16,384-byte response limit. A simulated valid 60-object response of 28,321 bytes reproduces HTTP 502 after the simulated deletion when Content-Length is supplied. Without that header, the response starts with status 200 but reading its stream fails. It is not guaranteed to be 502/503, and not every 60-object response has the attachment's quoted 18-25 KB size. No real files were deleted and no hosted failure was reproduced. See primary-source notes below.
